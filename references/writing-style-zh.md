# IP Spec 中文技术写作规范（默认启用）

面向读者：RTL 设计、验证、SoC 集成工程师。目标是让工程师**读懂电路的实际行为**，不是向读者解释 Agent 做了哪些谨慎动作。文档仍按 `spec-contract.md` 保留全部章节、表格、源代码引用和 VCS/Verdi 证据。

## 1. 按功能解释电路

- 每个功能小节先回答「这个模块做什么」，再回答「什么条件下发生」「在哪个时钟沿发生」「输出怎样变化」。把信号名放在自然语句里，不要逐行翻译 Verilog。
- 最重要的接口条件直接写成可检验的规则。例如：「在 `clk` 上升沿，若 `in_valid` 和 `in_ready` 同时为 1，模块接收 `in_data`。」不要写「在一定条件下实现数据交互」。
- 寄存器行为按「复位值 → 更新条件 → 保持条件 → 外部可见影响」说明。描述组合信号时把组合条件和触发沿区分清楚。
- 用短段落讲清一个问题。复杂接口先给一段直观解释，再列端口表、状态表、逐周期时序表；不要把表格中每一个数重复抄回正文。
- 中文为默认叙述语言。端口名、参数名、RTL 表达式、命令、信号高低电平和数字必须保留原样。英文专业名词首次出现时可附一次中文解释，其后统一称呼。

## 2. 去掉机器味和套话

优先删除下列没有新增技术信息的表达：

- 「需要注意的是」「值得一提的是」「综上所述」「总体而言」「从某种意义上讲」「众所周知」。直接写它后面的事实。
- 「本模块旨在实现……」「通过采用……机制来实现……功能」「从架构层面来看……」。改成「模块负责……」「当……时……」。
- 「赋能」「有效提升」「充分保障」「全面确保」「实现闭环」「体现重要价值」。除非有对应的性能数据或可观察的行为，否则不用。
- 「如前所述」「显而易见」「下面将详细介绍」。让标题和段落承接关系，不加导游词。
- 不要在每段结尾补「该行为仅供参考」「不能证明功能正确」「不构成保证」等免责句。

尽量采用主动语态和工程师常用的陈述句。正式不等于拗口；允许适度解释「因此」「此时」，不使用聊天口吻和营销措辞。

## 3. 证据说明只放在需要的位置

- **正文讲行为**：概述、接口、时序、状态机、集成章节直接陈述已从源码确定的行为，并给出源码行号。
- **验证章节讲证据**：在第 12 章（模块第 8 章）的表格中分别列出 RTL 分析、VCS 编译/仿真、Verdi FSDB 与未执行项目。没有结果时写一次「未执行」，不写长段免责声明。
- **未解决的问题集中列出**：无法从 RTL 确定的配置、约束或外部依赖放到第 13 章（模块第 9 章）；若它会直接影响集成使用，在对应章节描述具体条件即可。
- **图题只需简短注明来源**：如「图 9-1 — 单笔写入时序（RTL 推导）」或「图 9-2 — 连续传输时序（VCS/Verdi 波形）」。完整日志、哈希、执行状态放验证矩阵及 `.meta.json`，不要在每张图下重复「不构成功能正确性证明」。
- **诚实但不啰嗦**：没有跑 VCS 就在验证矩阵写「未执行」；不能改写成「已通过」。对于没有数据支持的指标，不编造频率/吞吐率/延迟。

这套规则只改变写法，不删除真实限制、复位约束、不可支持的协议条件，也不修改 RTL 事实和验证记录。

## 4. 改写示例（仅为句式示范，必须以实际 RTL 为准）

**握手（差）**：本模块旨在通过 ready/valid 机制实现数据交互。需要注意的是，只有在满足对应条件的情况下才能认为该事务发生。

**握手（好）**：当 `valid` 和 `ready` 在时钟上升沿同时为高时，接口完成一次传输。若 `ready=0`，发送端保持 `valid` 和数据不变，直到接收端准备好。（保持行为需由该设计的 RTL 支持。）

**复位（差）**：需要特别指出的是，本设计的复位行为可能受到实际仿真环境以及外部配置的多种影响，因此不能保证在所有情况下都有效。

**复位（好）**：`rst_n` 为低时，`out_valid` 和 `out_data` 异步清零。复位释放后，寄存器在下一个有效 `clk` 上升沿按输入握手条件更新。

**流水线（差）**：从整体实现架构的角度来看，可以认为设计在满足相应使能的前提下具有一定的流水线行为，但该推断未获得完备验证。

**流水线（好）**：一笔数据在第 N 个上升沿被接收，经过 3 级寄存器后，在第 N+3 个上升沿更新到输出。仅在连续使能且没有停顿时成立。——只有实际 RTL 能支持该延迟时才这么写。

## 5. Codex 成文后的最后一遍检查

1. 逐节阅读：读者能否知道「输入是什么、什么时候处理、结果什么时候有效」？
2. 删除没有技术信息的起承转合和一遍遍的风险声明；遇到真正的工程边界，用具体条件替代空泛担忧。
3. 检查所有改写保留信号名、时序沿、表达式、复位值、参数和 `file:line` 引用。
4. 运行 `scripts/style_lint.py --docs docs/rtl_spec --strict`，修复高置信度套话提示；语义质量仍靠通读，不依赖关键词脚本判定。
